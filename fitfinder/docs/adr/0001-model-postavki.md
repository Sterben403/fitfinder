# ADR-001: Выбор модели поставки для проекта FitFinder

- Статус: принято
- Дата: 2026-09-23
- Автор: <ваше имя>

## Контекст

FitFinder — мобильный магазин одежды с ИИ-поиском: пользователь фотографирует аутфит, система находит похожие товары в каталоге. Проект выполняется одним человеком (я совмещаю роли владельца продукта, менеджера и разработчика) в течение осеннего семестра 2026 года. Результат нужно показывать каждую неделю на лабораторных занятиях. Качество ИИ-поиска заранее неизвестно — это главная гипотеза, которую надо проверить.

## Движущие силы решения

- Команда из одного человека — процесс не должен требовать нескольких ролей и частых встреч
- Высокая неопределённость требований в ИИ-части (точность поиска, какие вещи распознавать)
- Жёсткий срок — конец семестра, еженедельные контрольные точки по лабораторным
- Нужны прозрачность и артефакты для преподавателя (доска, история решений)
- Нельзя допустить, чтобы к концу семестра не было работающего продукта

## Рассмотренные варианты

1. Каскадная модель (Waterfall)
2. Scrum
3. Kanban
4. Scrumban (Kanban-доска + недельные итерации)

## Решение

Выбран вариант 4 — **Scrumban с недельными итерациями**.

Доска с WIP-лимитами (In progress ≤ 2, Review ≤ 2) показывает поток работы и не даёт начинать много задач сразу. Недельная итерация совпадает с ритмом лабораторных: в начале недели планирование, в конце — демонстрация и короткая ретроспектива. Срок и качество фиксированы, **переменная величина — объём**: если ИИ-поиск займёт больше времени, второстепенные функции (избранное, фильтры) переносятся в бэклог.

### Почему отвергнуты другие варианты

- **Waterfall — отвергнут.** Требует полностью зафиксировать требования в начале, а качество ИИ-поиска можно узнать только экспериментом. Работающий продукт появился бы только в конце семестра, риск ничего не показать слишком высок.
- **Scrum — отвергнут.** Требует трёх отдельных ролей (Product Owner, Scrum Master, команда) и полный набор церемоний. Для одного человека это формальность, которая съедает время разработки.
- **Kanban — отвергнут.** Хорошо подходит для потока, но не имеет встроенного ритма и сроков. Для курса с еженедельными контрольными точками это ослабляет контроль сроков.

## Последствия

### Положительные
- Минимум процессных затрат, почти всё время уходит на разработку
- Быстрая реакция на результаты экспериментов с ИИ-моделью
- Каждую неделю есть видимый результат для преподавателя
- WIP-лимиты защищают от множества начатых и незаконченных задач

### Отрицательные
- Нет внешнего контроля: вся дисциплина держится на одном человеке, легко пропустить планирование или ретроспективу
- Нет код-ревью другим человеком — выше риск ошибок (частично закрывается автотестами и чек-листом ревью)
- Переменный объём: к концу семестра часть желаемых функций может не войти в продукт
- Оценки задач (S/M/L) субъективны, прогнозировать сроки сложнее, чем в каскадной модели

## Критерий пересмотра

Решение пересматривается, если выполняется хотя бы одно условие:
- в команду добавляется 2 и более человека (тогда рассмотреть Scrum);
- две итерации подряд не выполнено больше половины запланированных задач;
- появляется внешний заказчик с фиксированным ТЗ и контрактом.
